# SUMO V2X Rear-End Collision Warning Scenario

This project provides a reproducible single-lane emergency-braking scenario.
Vehicle states are sent to a Multi-access Edge Computing (MEC) server through
a UE network interface, and the actual arrival time of the MEC warning affects
when the following vehicle begins braking.

## Scenario Timeline

```text
0.0 s                  5.0 s                   warning + 0.3 s
  │                      │                           │
  ├── Cruise at 20 m/s ──┼── Leader brakes at ──────┼── Follower brakes
  │     28 m net gap      │      8 m/s²              │
  └──────────────────────┴───────────────────────────┴────────────
```

- `leader_car`: red lead vehicle.
- `follower_car`: blue following vehicle; it turns yellow when a warning is
  received.
- Without a valid MEC warning, the follower brakes after a 1.5-second driver
  reaction delay.
- Vehicle states are reported every 0.1 seconds by default, resulting in a
  10 Hz reporting rate.
- The simulation is synchronized with wall-clock time by default. HTTP
  requests run in the background and do not freeze the SUMO simulation clock.

The GUI scene includes a marked emergency-braking test zone, grass verges,
sidewalks, a control center, parking spaces, tree rows, vehicle labels, and
V2X/MEC markers. The camera automatically tracks the following vehicle.

## Project Files

| File | Purpose |
|---|---|
| `sumo_ue_sender.py` | TraCI scenario control, asynchronous MEC communication, and measurements |

| `viewsettings.xml` | GUI colors, labels, zoom, and display settings |

| `requirements-mec.txt` | Python dependencies for `app.py` |
| `outputs/` | Per-run CSV, JSON, FCD, tripinfo, and collision output |

## Quick Start

### 1. Baseline Test Without MEC

Run a fast headless verification:

```bash
python3 sumo_ue_sender.py --dry-run
```

Watch the baseline scenario in the GUI and in real time:

```bash
python3 sumo_ue_sender.py --mode baseline --gui --realtime
```

The baseline configuration is expected to produce a rear-end collision. It is
used as the control case when evaluating the benefit of MEC warnings.

### 2. Local Mock MEC

In the first terminal:

```bash
python3 mock_mec_server.py
```

In the second terminal:

```bash
python3 sumo_ue_sender.py \
  --mode mec \
  --mec-url http://127.0.0.1:18080/mec/v2x/sumo/report \
  --ue-interface '' \
  --gui \
  --realtime
```

The mock MEC sends a warning when TTC is less than or equal to 4 seconds and
adds a 10 ms processing delay by default. Use `--delay-ms` to emulate a longer
server-side delay.

### 3. Deploy the Same App on MEC and WAN

Copy the same `app.py` and `requirements-mec.txt` to both servers. Install and
start the service:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-mec.txt
```

On the MEC server:

```bash
DEPLOYMENT_MODE=mec \
MEC_ADDED_DELAY_MS=0 \
TTC_WARNING_THRESHOLD_S=4 \
uvicorn app:app --host 0.0.0.0 --port 8000
```

On the external WAN server:

```bash
DEPLOYMENT_MODE=wan \
WAN_ADDED_DELAY_MS=500 \
TTC_WARNING_THRESHOLD_S=4 \
uvicorn app:app --host 0.0.0.0 --port 8000
```

Both profiles execute exactly the same TTC algorithm. The WAN profile defaults
to a controlled 500 ms application delay so that the experiment remains
repeatable and demonstrates a late-warning collision under the scenario's
current timing. This delay is returned by the API as
`configured_delay_ms`, written to the network CSV, and must be reported as an
emulated WAN delay rather than natural Internet latency. Set
`WAN_ADDED_DELAY_MS=0` to measure only the real network path.

Verify each deployment before starting SUMO:

```bash
curl http://MEC_SERVER:8000/status
curl http://WAN_SERVER:8000/status
```

The first response must contain `"architecture":"mec"` and the second must
contain `"architecture":"wan"`.

Run the MEC trial:

```bash
python3 sumo_ue_sender.py \
  --mode mec \
  --mec-url http://MEC_SERVER:8000/mec/v2x/sumo/report \
  --ue-interface uesimtun0 \
  --max-inflight 8 \
  --gui \
  --realtime
```

Run the WAN trial with a different run ID:

```bash
python3 sumo_ue_sender.py \
  --mode wan \
  --mec-url http://WAN_SERVER:8000/mec/v2x/sumo/report \
  --ue-interface uesimtun0 \
  --mec-timeout 3 \
  --max-inflight 8 \
  --gui \
  --realtime
```

Using `uesimtun0` for both endpoints gives a fair comparison when the external
server is reachable through the UE data path. If the external server must use
the host's normal route, use `--ue-interface ''` for the WAN command and record
that routing difference with the results.

With the default scenario and controlled delay, the expected result is:

| Deployment | Added delay | Typical result |
|---|---:|---|
| MEC | 0 ms | Warning is applied and collision is avoided |
| WAN | 500 ms | Warning arrives after fallback is committed and collision occurs |

### 4. Real UE and MEC

First, verify that the UERANSIM UE tunnel exists:

```bash
ip link show uesimtun0
```

Then run:

```bash
python3 sumo_ue_sender.py \
  --mode mec \
  --mec-url http://172.16.6.100/mec/v2x/sumo/report \
  --ue-interface uesimtun0 \
  --gui \
  --realtime
```

The MEC URL, UE interface, and UE ID can also be configured through environment
variables:

```bash
export MEC_URL=http://172.16.6.100/mec/v2x/sumo/report
export UE_INTERFACE=uesimtun0
export UE_ID=ueransim-ue-001
python3 sumo_ue_sender.py
```

To use the operating system's normal routing table instead of a specific UE
tunnel, pass an empty interface:

```bash
python3 sumo_ue_sender.py --ue-interface ''
```

## Execution Modes

| Mode | Behavior |
|---|---|
| `mec` | Sends vehicle states and acts on the first valid, non-stale MEC warning |
| `wan` | Uses the same live-response path but labels the trial as WAN |
| `baseline` | Does not contact MEC and uses only the 1.5-second driver reaction delay |
| `mec-timeout` | Generates no network requests and reproduces the no-response fallback path |

Common options:

```text
--send-rate 10
--warning-reaction-time 0.3
--fallback-reaction-time 1.5
--max-response-age 1.0
--mec-timeout 2.0
--max-inflight 4
--no-gui
--no-realtime
```

`--no-realtime` is useful for baseline and offline testing. Keep `--realtime`
enabled for live MEC experiments; otherwise, the simulation may finish before
HTTP responses arrive.

## MEC JSON Contract

The existing required request fields remain unchanged:

```json
{
  "scenario": "rear_end_emergency_brake",
  "ue_id": "ueransim-ue-001",
  "sim_time": 5.8,
  "client_send_ts": 1785139194.8,
  "vehicles": [
    {
      "vehicle_id": "leader_car",
      "x": 198.0,
      "y": -1.6,
      "speed": 13.6,
      "accel": -8.0,
      "lane_id": "main_road_0",
      "lane_pos": 198.0,
      "length": 5.0
    }
  ]
}
```

The sender also includes `run_id`, `sequence`, and `event_state`. Existing MEC
implementations may safely ignore these additional fields.

Expected risk information in the response:

```json
{
  "service": "v2x-collision-warning",
  "version": "2.0.0",
  "architecture": "mec",
  "configured_delay_ms": 0.0,
  "compute_delay_ms": 0.03,
  "server_recv_ts": 1785139194.81,
  "server_send_ts": 1785139194.82,
  "proc_delay_ms": 0.04,
  "client_ip": "10.0.0.2",
  "result": {
    "gap": 24.4,
    "relative_speed": 7.2,
    "ttc": 3.39,
    "risk_level": "warning",
    "warning": true,
    "leader_id": "leader_car",
    "follower_id": "follower_car"
  }
}
```

A warning is accepted only when:

- `warning` is the JSON boolean `true`.
- The leader and follower IDs match the controlled vehicles.
- The response age does not exceed `--max-response-age`.

## Output Files

Each run receives a unique `run_id` based on the current time and a random
suffix. A fixed ID can be supplied with `--run-id`.

- `<run_id>_steps.csv`: local ground truth for every SUMO simulation step.
- `<run_id>_network.csv`: MEC RTT, server timing, and risk result for every
  completed request, including server architecture and configured delay.
- `<run_id>_summary.json`: collision outcome, minimum gap/TTC, warning time,
  braking time, server architecture, configured delay, and RTT statistics.
- `<run_id>_fcd.xml`: SUMO floating-car data.
- `<run_id>_tripinfo.xml`: SUMO trip information.
- `<run_id>_collisions.xml`: SUMO collision records.

## Rebuilding the Network

After editing `nodes.nod.xml` or `edges.edg.xml`, regenerate the network:

```bash
netconvert \
  --node-files nodes.nod.xml \
  --edge-files edges.edg.xml \
  --output-file road.net.xml \
  --no-turnarounds true
```

The project has been verified with Eclipse SUMO 1.27.0. Python first attempts a
normal `import traci`. If that fails, it automatically loads TraCI from
`/usr/share/sumo/tools` or `$SUMO_HOME/tools`.
